OutputViewAgent 实现方案对比

三种方案的核心区别在于后端如何生成 spec 和前端如何消费

A

方案A：后端直出完整 spec + 前端流式渲染

核心思路：OutputViewAgent 的系统提示词包含 catalog 定义的完整描述，让 LLM 直接输出符合 json-render schema 的 spec JSON。后端通过 AGENT_OUTPUT 事件逐 chunk 发送 JSONL patch，前端用 createSpecStreamCompiler 渐进渲染。

优势

  • LLM 直接输出 spec，无需额外转换层
  • 天然支持流式 — JSONL patch 逐行应用
  • catalog.prompt() 可自动生成 AI 提示词

劣势

  • LLM 必须严格遵循 spec 格式，输出质量依赖提示词
  • 图表组件需要前端自行实现渲染逻辑
B

方案B：后端输出结构化数据 + 前端模板映射

核心思路：后端 LLM 输出简洁的结构化 JSON（如 {"type": "bar_chart", "data": {...}}），后端或前端将其转换为 json-render spec。LLM 只需关心数据内容，不需要理解 spec 结构。

优势

  • LLM 输出更简洁，格式错误率低
  • 解耦数据与渲染，灵活调整展示方式

劣势

  • 需要额外的转换层（后端或前端）
  • 流式支持更复杂 — 需要等待完整 JSON 再转换
  • 自定义数据格式需要额外维护
C

方案C：混合方案（推荐）

核心思路：结合 A 和 B 的优点。定义一套精简的"视图描述协议"（View Description Protocol），LLM 输出该协议格式的 JSON，同时该协议格式就是 json-render spec 的子集。通过 catalog 的 prompt 引导 LLM 输出正确的 spec，关键约束用 Zod schema 强制校验。

优势

  • catalog.prompt() 自动生成提示词，LLM 输出质量可控
  • 支持流式渲染 — spec 本身就是 JSONL patch 兼容
  • 前端 catalog 定义 + registry 实现解耦，可独立迭代组件样式
  • 图表用 ECharts 组件封装，spec 只描述数据，渲染逻辑在前端

劣势

  • 需要同时维护前端 catalog 和后端提示词同步
  • 首次实现工作量稍大

方案对比总结

维度 A: 直出 spec B: 数据+模板 C: 混合(推荐)
流式渲染 原生支持 需要额外处理 原生支持
LLM 输出质量 依赖提示词 格式简洁可控 catalog引导+Zod校验
实现复杂度 中 中高 中
可扩展性 高 中 高
与json-render契合度 完美 需要转换层 完美
